Architecture and cryptography

The central design decision is simple. The browser owns readable workout state. The API provides optional account sessions, proof verification, and opaque encrypted storage. Local mode works without an account and does not run the account proof flow. The ZK layer is a scoped proof-carrying sync experiment, not a claim that the whole application is formally verified.

Plaintext workout state, private keys, public key material, analytics, proof generation, and the encryption boundary are in the browser. IndexedDB stores an encrypted record. An optional HTTP-only JWT session connects the browser to the Node.js and Express API. The API verifies proof metadata, stores a nullifier, and stores opaque encrypted payloads in PostgreSQL without receiving readable workout state.

The service worker caches static application assets for offline startup. It does not intercept API requests. IndexedDB stores the encrypted blob and the optional KEM ciphertext, not the parsed workout object.

Data flow

  1. The user enters a password in the browser during account registration or login.
  2. Argon2id stretches the password. HKDF expands the result into deterministic seeds for the ML-DSA and ML-KEM key pairs.
  3. The server issues a login nonce. The client signs it with ML-DSA-65. The API returns an HTTP-only JWT session cookie after verification.
  4. The client serializes workout state and encrypts it with AES-256-GCM using a random 12-byte IV.
  5. In account mode, ML-KEM-768 encapsulates a fresh shared secret that becomes the AES data key for the payload.
  6. The browser computes a Groth16 proof over the private workout summary, identity secret, state nonce, thresholds, and a field binding of the encrypted blob plus KEM ciphertext.
  7. The browser stores the encrypted record locally and can send it with the proof and public signals to the API for optional account sync.
  8. The API verifies the proof, checks the identity commitment, rejects a reused nullifier, and then PostgreSQL stores the opaque values.
  9. On retrieval, the client decapsulates and decrypts the payload before calculating analytics.

Cryptography decision table

Concern Algorithm Why it is used What it does not guarantee
Password-derived key material Argon2id plus HKDF with SHA-256 Slows password guessing and separates derived material into key seeds. It does not make a weak password safe or protect a compromised device.
Login authentication ML-DSA-65 Proves possession of the client signing key without sending the private key. It does not establish device trust or provide password recovery.
Sync data-key encapsulation ML-KEM-768 Creates a fresh shared secret for an encrypted sync payload. It does not solve availability, replay, deletion, or conflict resolution.
Workout validity proof Groth16, Circom, and Poseidon Lets the API verify private summary rules, identity knowledge, commitments, nullifiers, and an encrypted-record binding. It does not prove AES-GCM or ML-KEM internals, prove that ciphertext decrypts to the summary, or protect a compromised browser.
Payload confidentiality and integrity AES-256-GCM Encrypts serialized workout state and detects modified ciphertext. It does not protect plaintext while the app is running or hide all metadata.

Why post-quantum cryptography is included

ML-DSA-65 and ML-KEM-768 are an engineering exploration, not a claim that a fitness app commercially requires post-quantum algorithms. Groth16 and Poseidon are also used as a scoped proof experiment. The proof does not cover AES-GCM or ML-KEM internals, and it does not prove that the ciphertext decrypts to the private summary. This project does not claim an independent cryptographic audit or a guarantee against every future threat.

What is not implemented

  • No independent security review, penetration test, formal verification, or certification
  • No production-grade trusted setup. The checked-in development artifact is reproducible with a deterministic local contribution and is not a multi-party ceremony
  • No complete browser and device matrix
  • No password reset or account recovery flow
  • No automated two-browser cross-device test or conflict resolution
  • No high-availability, backup, alerting, incident response, or service-level evidence
  • Local demo mode uses a fixed application key and cannot protect against code running in the same origin
